Adopt these grafts from candidate 2:

1. Select applicable active policies and corrections before ranked evidence. Give restrictions an explicit context budget and visible overflow behavior. An incomplete restriction set cannot silently count as complete permission context.
2. Define distinct Intent, Policy, Observation, and Interpretation kinds. Keep lifecycle separate from evidence availability and freshness. Preserve candidate 1's expiry support and the rule that changed code does not revoke continuing policy.
3. Make capture validation an application contract. The existing local model may propose capture during its normal turn. Rust checks source excerpts, source identity, scope, IDs, and transitions. Persist before acknowledging memory. Keep candidate 1's successful-operation boundary for SQL receipts.

Resolve these issues before marking implementation children ready:

- Define forget and withdrawal durability. Removing current files and rebuilding SQLite does not prevent an older branch, interrupted replay, or restored duplicate from reintroducing the content. Specify a minimal content-free local suppression record, its scope and lifetime, and explicit restoration behavior. Distinguish this from the separate Git-history limitation. Do not claim deletion across every checkout when only the active checkout is managed.
- Define receipt ordering around a crash after a SQL write but before the receipt is saved. An operation ID alone cannot prove completion. Recovery must reconcile the observed artifact conservatively and report missing provenance instead of inventing success. Neither design needs a general event log to meet this contract.
- Verify durable project access, linked-worktree metadata, accepted file operations, FTS5, and the model's capture and response limits. Assign these to A, B, and the capture child rather than leaving a collective preimplementation checklist. Candidate 2's explicit 128-token baseline makes output feasibility particularly visible.
- Retain candidate 1's ignored capture area, but specify how a request such as "share this" moves the existing ID into tracked knowledge. This is an ordinary authorized action, not a second approval ritual. Initial project-memory activation must not become a repeated correction approval.
- State the eventual `.piarre/skills` location explicitly in the synthesized roadmap. Keep compatibility work early and OpenSpec migration in M5. The proposed `.piarre` target is not evidence that current tools support relocation.

Both candidates converge on bounded exact and FTS retrieval, readable provenance, provisional inference, local restrictions, and later merge assistance and compression. Keep those shared choices. Do not graft candidate 2's persistent-volume recommendation without resolving how the selected Git project enters and leaves it.
