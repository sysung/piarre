### P3: Choose proportionate workflow with one knowledge home

> *This was generated by AI during triage.*

**Category/state recommendation:** enhancement / needs-triage.

**Current behavior:** The current PoC has no adaptive workflow selector; existing planning lives in native OpenSpec paths.

**Outcome:** Ordinary requests receive Direct, Light plan, or Spec-driven treatment proportionate to known impact, ambiguity, explicit preference, and accepted policy. PKM, project skills, and AI workflow artifacts use `.piarre/`; code, tests, and ordinary docs stay outside.

**Children:** To be designed later. **Blocker for implementation:** P2, including its qualified specification foundation.

**Out of scope:** Default fork adoption, duplicate specs, a second required model, or assuming deterministic policy alone can understand arbitrary impact. Split implementation children only after T0 evidence and design review.

## Publication and triage procedure

When publication is requested, use this sequence:

1. Refresh live milestones, issues/comments, labels, rejection records, and Project 8. If an overlapping tracker appeared, reuse it rather than duplicate it. Flag conflicting state labels before changing them.
2. Ensure the reviewed planning artifacts have a stable published source link. Do not invent a blob URL on an unpushed branch. If publishing before source push is desired, explicitly choose a reviewable source attachment or inline contract.
3. Present the `enhancement` / `needs-triage` recommendation for the concrete drafts. The user may override states; unresolved feasibility is not agent-ready work.
4. Create or reuse the six named milestones and six parent trackers. Then create T0-T7, each with the triage disclaimer, milestone, and exactly one category/state pair.
5. Resolve placeholders to actual issue numbers and database IDs. Add native parent/sub-issue relations and native blockers in the dependency map. Attach relevant items to Project 8 using observed field values.
6. Read back issue bodies, parent relations, blockers, labels, and milestone assignments. Record actual URLs in a publication map; do not use closed historical research as proof of completed prerequisites.
7. Triage the next unblocked child against its current implementation. Post a durable agent brief only after scope, authority, prerequisites, and verification are concrete. Reserve `ready-for-human` for actual human work such as final acceptance.

Each worked issue and PR must link back to each other and to the owning OpenSpec contract and verification section. Later-stage child briefs are authored only when the corresponding design is ready. Do not auto-enable skills/hooks or create verification infrastructure as a side effect of publishing the roadmap.
