# Cross-judge verdict

Choose **Sol as the base, with two narrow grafts from Astra**. Sol removes the observed path from a correct calculation to a contradictory generated numerical conclusion. Astra explicitly retains that path. Neither establishes source meaning or authority, and neither demonstrates an improvement before execution.

This is a document review, not measured prototype performance. Both packages compare two distinct whole-shape alternatives. No inference, generated-code execution, or repository changes were performed.

## Evidence behind the scores

**Bounded execution.** Both use closed arithmetic grammars, anchored literals, finite rational bounds, division checks, and consumed call reservations. Sol's backward-only rows are slightly simpler to bound than Astra's recursive trees. Neither executes generated code.

**Grounding.** Both correctly distinguish quotation identity and arithmetic validity from operand relevance, operator choice, source authority and prerequisite completeness. Sol adds a full-original-evidence semantic audit but explicitly acknowledges correlated self-approval. That is a hypothesis worth measuring, not independent verification.

**Simplicity.** Both expose one deep operation and three files. Sol additionally owns comparison orchestration, resumable run identity, a unit registry and task-shaped decision types. Those increase prototype scope. Astra's one-arm entry point and absence of claimed dimensional validity are smaller. Do not import production integration, domain rules, or a generalized unit-conversion system.

**Completion.** Sol deterministically renders numerical relations, directly addressing the known contradiction. Its numeric schema cannot express a complete mixed answer containing mandatory nonnumeric conditions; rejection is honest but remains task failure. Astra preserves unrestricted mixed prose, but its final parser checks only nonblank text and citation membership. It consequently leaves the demonstrated numerical-prose failure mechanically possible. Neither merits full credit here.

**Comparison.** Both retain original evidence, propose a strong two-call direct control, count failures, and freeze before fresh validation. Sol explicitly limits every complete prompt to 6,000 UTF-8 bytes and output to 1,024 tokens. Astra bounds the original inquiry and mentions separate envelope/generation caps without specifying the required complete-request/output ceilings. Its 24-call development screen is broader but more expensive than the initial feasibility question requires.

## Two precise grafts

1. **Use Astra's numerical relation vocabulary inside Sol's deterministic renderer.** Replace `capacity` and `minimum` task labels with value or comparison outputs using `lt/le/eq/ge/gt`, plus an optional computed difference. Render “The selected quantities satisfy this numerical comparison” with values and source citations. Never render eligibility, safety, permission or an unconditional task-level yes. Keep Sol's operation table and audit. This avoids a growing task-template taxonomy while still preventing numerical-prose reversal. Unsupported mixed answers must remain explicit failures, counted in full-response scoring.

2. **Use Astra's code-derived contributing-source union.** Derive numerical citations from referenced quantities and operation dependencies. Do not trust a model-authored citation list for computed outputs. Preserve each original status and label the interpretation unverified even after audit acceptance.

## Minimum experiment and stop rule

Retain Sol's offline-first, eight-call feasibility screen. Make its arithmetic case include a mandatory nonnumeric prerequisite; make the other case a nonarithmetic missing-fact question. Judge the whole final answer, not just computed values or schema success. This screen can reject the design, never establish superiority.

Freeze the revised schemas, prompts, renderer, bounds and baseline before independently authored fresh paired validation. If deterministic output improves arithmetic while losing required conditions or ordinary task completion, scrap or narrow the approach rather than adding task-specific templates. Explicitly enforce two calls per arm, 1,024 requested output tokens, and 6,000 bytes per complete prompt.
